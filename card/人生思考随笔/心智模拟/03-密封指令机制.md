# 密封指令机制：设计者与执行者的分离

## 核心问题

**如何确保"设计者"在制定计划后不干扰"执行者"的执行?**

这是整个系统最关键的机制,解决"不能同时做裁判和选手"的矛盾。

## 密封指令的概念

### 定义
密封指令是一个**不可在执行期间修改**的行动计划,一旦进入"执行者"模式,系统将拒绝任何来自"设计者"的修改请求。

### 类比
- 就像法律文件签字后的生效期
- 就像实验设计中的"双盲"机制
- 就像爱迪生入睡前的"委托"

## 密封指令的生命周期

### 阶段1: 设计阶段 (设计者模式)

**允许的操作**:
- 定义目标条件
- 设定外在逻辑(规则)
- 探索不同方法
- 反复横跳校准感知
- 双侧刺激(尝试极端A和极端B)

**输出**:
```json
{
  "instruction_id": "INS_001",
  "status": "designing",
  "goal": "建立每日冥想习惯",
  "rules": [
    "每天早上7:00-7:15",
    "使用客厅的瑜伽垫",
    "使用Headspace应用",
    "不允许跳过,即使只有5分钟也要做"
  ],
  "method": "从5分钟开始,每周增加2分钟",
  "duration": "21天",
  "checkpoints": [
    {"day": 7, "type": "短期检查"},
    {"day": 21, "type": "完整评估"}
  ],
  "created_by": "设计者",
  "created_at": "2025-11-11T08:00:00"
}
```

### 阶段2: 密封阶段 (过渡)

**触发条件**:
- 设计者明确表示"我准备好了"
- 目标和规则已经明确定义
- 所有必要的资源已经准备

**密封操作**:
```json
{
  "instruction_id": "INS_001",
  "status": "sealed",
  "sealed_at": "2025-11-11T20:00:00",
  "sealed_until": "2025-12-02T20:00:00",
  "modification_lock": true,
  "designer_access": "read_only",
  "executor_access": "execute_only"
}
```

**系统承诺**:
- 在密封期间,设计者**不能**修改目标、规则、方法
- 设计者**只能**在检查点查看进度
- 执行者**只能**按照指令执行,不能质疑

### 阶段3: 执行阶段 (执行者模式)

**执行者的行为**:
- **Just do it**: 不思考"为什么",只关注"怎么做"
- **黑盒运作**: 不向设计者报告实时进度
- **自动化**: 尽可能减少决策点

**设计者的限制**:
```python
# 伪代码示例
def designer_tries_to_modify(instruction_id, new_rule):
    instruction = get_instruction(instruction_id)
    
    if instruction.status == "sealed":
        if current_time < instruction.sealed_until:
            return {
                "success": False,
                "message": "指令已密封,无法修改",
                "next_checkpoint": instruction.next_checkpoint(),
                "suggestion": "请等待检查点,或者创建新的指令"
            }
    
    # 只有在检查点或密封期结束后才允许修改
    return modify_instruction(instruction_id, new_rule)
```

### 阶段4: 检查点 (设计者短暂回归)

**检查点的作用**:
- 设计者查看执行结果
- 评估是否达成预期
- 决定是否继续、调整或终止

**检查点流程**:
```
1. 系统触发检查点通知
2. 执行者暂停,生成报告
3. 设计者登场,审查报告
4. 设计者做出决策:
   a) 继续执行(重新密封)
   b) 调整参数(修改后重新密封)
   c) 终止指令(解封并归档)
5. 如果继续,执行者重新接管
```

### 阶段5: 解封与评估

**解封条件**:
- 密封期到期
- 目标已达成
- 遇到无法处理的异常
- 设计者强制解封(需要确认)

**最终评估**:
```json
{
  "instruction_id": "INS_001",
  "status": "completed",
  "unsealed_at": "2025-12-02T20:00:00",
  "execution_summary": {
    "total_days": 21,
    "completed_days": 19,
    "skipped_days": 2,
    "average_duration": "8.5分钟"
  },
  "designer_evaluation": {
    "goal_achieved": true,
    "satisfaction": 8,
    "lessons_learned": [
      "早上时间确实更容易坚持",
      "5分钟起步很有效,降低了心理门槛"
    ],
    "new_beliefs": [
      "渐进式增加比一开始设定高目标更有效"
    ]
  }
}
```

## "骗过自己"的技术实现

### 1. 物理隔离

**UI设计**:
- **设计者界面**: 复杂、多选项、鼓励思考
- **执行者界面**: 极简、单一行动按钮、无选择

**示例**:
```
设计者界面:
┌─────────────────────────────────┐
│ 目标设定                         │
│ [详细表单]                       │
│ [多种方法选择]                   │
│ [参数调整滑块]                   │
│ [模拟结果预测]                   │
│ [保存] [密封并启动]              │
└─────────────────────────────────┘

执行者界面:
┌─────────────────────────────────┐
│                                 │
│    今日任务: 冥想15分钟          │
│                                 │
│         [开始执行]               │
│                                 │
│    (无其他选项)                  │
└─────────────────────────────────┘
```

### 2. 时间隔离

**自然遗忘机制**:
- 设计阶段通常在晚上(理性思考时间)
- 执行阶段在早上(行动时间)
- 利用睡眠作为"状态切换"的自然边界

**提醒策略**:
- 设计者模式: 不发送提醒(避免打断思考)
- 执行者模式: 精准提醒(触发自动化行为)

### 3. 认知隔离

**语言风格切换**:
```
设计者模式的LLM:
- 使用疑问句: "你确定这个方法可行吗?"
- 提供多个选项: "你可以选择A、B或C"
- 鼓励反思: "让我们分析一下利弊"

执行者模式的LLM:
- 使用祈使句: "现在开始冥想"
- 只有一个指令: "按照计划执行"
- 避免思考: "不要想太多,直接做"
```

### 4. 社会承诺机制

**可选的外部监督**:
- 向朋友/家人声明目标
- 公开进度(社交压力)
- 设置违约惩罚

## LLM在密封机制中的角色

### 1. 密封前的确认对话

```
LLM: "你已经设定了以下目标和规则:[总结]。
      一旦密封,在接下来的21天内,你将无法修改这些规则。
      你确定准备好了吗?
      
      如果还有疑虑,我们可以继续调整。
      如果准备好了,请输入'我准备好了'来密封指令。"

用户: "我准备好了"

LLM: "指令已密封。从明天早上7:00开始,你将进入执行者模式。
      我会在第7天和第21天提醒你进行检查。
      在此期间,专注执行,不要质疑。祝你成功!"
```

### 2. 执行期间的"拒绝修改"对话

```
用户: "我觉得早上7点太早了,能改成8点吗?"

LLM: "我理解你的想法,但这个指令目前处于密封状态。
      
      当初你选择7点是基于[原因]。
      
      修改规则会破坏'执行者模式'的完整性。
      
      你有两个选择:
      1. 继续按照7点执行,在第7天的检查点重新评估
      2. 强制解封(但这会终止当前的21天挑战)
      
      你想怎么做?"
```

### 3. 检查点的引导对话

```
LLM: "今天是第7天检查点。让我们回顾一下:
      
      执行情况:
      - 完成: 6/7天
      - 平均时长: 8分钟
      - 跳过: 1天(11月15日,原因:出差)
      
      你对这个进度满意吗?
      你想继续、调整还是终止?"

用户: "继续,但我想把时间增加到10分钟"

LLM: "很好!我会更新指令,将目标时长改为10分钟。
      新的密封期将从明天开始,到第21天结束。
      准备好了吗?"
```

## 防止"偷懒"的机制

### 问题
如果执行者在执行时可以调整,就会倾向于选择更容易的路径。

### 解决方案

1. **二进制执行记录**
   - 只记录"完成"或"未完成"
   - 不记录"完成了一半"或"做了类似的事"

2. **无中间选项**
   - 不允许"今天只做5分钟"(如果目标是15分钟)
   - 要么完整执行,要么标记为跳过

3. **跳过的代价**
   - 跳过会重置连续天数
   - 跳过会在检查点被高亮显示
   - 跳过超过阈值(如3次)会触发强制检查点

## 技术实现要点

### 数据库设计
```sql
CREATE TABLE sealed_instructions (
    id UUID PRIMARY KEY,
    user_id UUID,
    status ENUM('designing', 'sealed', 'completed', 'terminated'),
    sealed_at TIMESTAMP,
    sealed_until TIMESTAMP,
    modification_lock BOOLEAN,
    content JSONB,
    checkpoints JSONB,
    execution_log JSONB
);

CREATE TABLE modification_attempts (
    id UUID PRIMARY KEY,
    instruction_id UUID,
    attempted_at TIMESTAMP,
    attempted_by ENUM('designer', 'executor'),
    modification_type VARCHAR,
    was_allowed BOOLEAN,
    reason TEXT
);
```

### API设计
```
POST /instructions/seal
GET /instructions/{id}/status
POST /instructions/{id}/execute (执行者专用)
POST /instructions/{id}/modify (设计者专用,检查密封状态)
GET /instructions/{id}/checkpoint
POST /instructions/{id}/unseal
```
