# 通用状态机框架：可注入的属性指标、算法、事件库与路径规划

> **定位**：本文从午餐系统与 MindFlow 行为系统的共同底层范式出发，设计一套通用状态机框架——它允许使用者注入不同的属性指标、事件库、路径规划算法和随机层配置，形成一套「设计者不再需要反复设计，执行者不再需要反复决策」的运转系统。

---

## 零、两个系统，同一套骨架

把午餐系统和 MindFlow 放在一起看，剥掉菜谱名称和心理学术语的外壳，它们剩下的是完全相同的结构：

| 通用层 | 午餐系统 | MindFlow |
|--------|---------|----------|
| **状态指标** | 饥饿度、饱腹感、清醒度、情绪 | 情绪、专注、动力、压力、精力（子层：多巴胺、皮质醇、血清素） |
| **状态边界** | 1-10 量表 | 0-100 量表 |
| **规则层** | 情绪低沉→强制映射温热修复型 | overlay：缺觉→专注恢复打75折、高压力→恢复收益乘1.4 |
| **事件库** | 12套菜谱（每套含热量、蛋白质、碳水、脂肪、食用效果） | 20+ 行为模板（每项含 delta、effects、tags） |
| **路径规划** | （当前为隐含的：掷骰子映射到某类，顺延规则） | 手动编制的行为链（sequences），尚未自动化 |
| **随机层** | 统一6面骰子 | 骰子从多套计算好的链中选一条 |
| **执行器** | 掷骰子→取菜→进食→记录→反馈 | tick_run→执行事件→写 state_delta→推进索引 |
| **检查点** | 连续两次无法执行时触发设计者介入 | 检查点事件（checkpoint_review_7min） |
| **反馈闭环** | 餐后30min/90min记录→周汇总→调参 | state_delta 记录→（尚未闭环回规划系统） |

这不是巧合。它们本质上都是一种 **具有随机化路径选择的、闭环校准的、有限状态机**。区别只在于注入的具体数据不同。

本文的目标，就是把这种共性抽象为一个可配置的通用框架。

---

## 一、框架总览：七层架构

```
┌─────────────────────────────────────────────────┐
│                   7. 配置层                       │
│     (一切皆可注入：属规、事件库、算法、随机策略)      │
├─────────────────────────────────────────────────┤
│                   6. 反馈闭环                     │
│     (记录实际效果 → 校准事件 delta → 更新规则)      │
├─────────────────────────────────────────────────┤
│                   5. 执行层                       │
│     (密封执行 → tick → 累计状态 → 检查点)           │
├─────────────────────────────────────────────────┤
│                   4. 随机层                       │
│     (从算法产出的候选集中随机选一条路径)             │
├─────────────────────────────────────────────────┤
│                   3. 路径规划层                    │
│     (状态空间搜索 → 多候选链 → 评分/排序)            │
├─────────────────────────────────────────────────┤
│                   2. 事件筛层                      │
│     (根据当前状态，从事件库中过滤可用事件)            │
├─────────────────────────────────────────────────┤
│                   1. 状态指标层                    │
│     (维度定义 + 边界 + 初始/目标模板 + 覆盖规则)      │
└─────────────────────────────────────────────────┘
```

每一层都是可替换的插件。一个领域（午餐、心智、理财、健身……）要接入这个框架，只需提供一套配置文件，注入这七层所需的数据结构和算法选择。

## 二、第一层：状态指标层（State Schema Layer）

这是整个系统的「坐标系」。所有事件的效果、路径规划的目标、覆盖规则的触发条件，都在这套坐标系的定义之上操作。

### 2.1 核心抽象

```yaml
# state_schema.yaml — 可跨领域复用的通用结构
schema:
  id: "my_domain_v1"
  name: "领域名称 v1"

  dimensions:
    - key: "cat_A.指标名"        # 用点分路径支持任意分组
      label: "显示名称"
      kind: int | float | enum   # 数值型或枚举型
      default: 50                # 初始默认值
      min: 0
      max: 100
      # 可选扩展字段:
      decay_per_tick: 0.0        # 每tick自然衰减量（比如精力随时间下降）
      ui_color: "#4CAF50"        # 前端展示用
      unit: "%"                  # 显示单位

    # 示例：三个领域分别注入不同的维度
    # ── 心智领域 ──
    - key: "subjective.专注"
    - key: "subjective.情绪"
    - key: "hormone.多巴胺"

    # ── 午餐领域 ──
    - key: "body.饥饿度"
    - key: "body.饱腹感"
    - key: "mental.清醒度"

    # ── 健身领域 ──
    - key: "body.体脂率"
    - key: "body.肌肉量"
    - key: "mental.训练意愿"

  # 意图到指标操作的映射（effect_mapping）
  # 将高层意图翻译为具体的维度操作
  effect_mapping:
    focus_gain:           # 意图名
      target: "subjective.专注"
      op: add
      ratio: 1.0
    stress_relief:
      target: "subjective.压力"
      op: add
      ratio: -1.0         # 负 ratio 表示 "减压" 即降低压力值

  # 覆盖层规则（overlays）——对行为效果的动态修正
  overlays:
    - id: "缺觉模式"
      priority: 200        # 优先级：高者在多规则匹配时优先生效
      when:
        all:
          - key: "objective.睡眠时长"
            op: lt
            value: 45
        # 支持 any / all / none 组合
      apply:
        - match_intent: "focus_gain"
          op: multiply
          value: 0.75
        - match_intent: "energy_gain"
          op: multiply
          value: 0.8
      message: "缺觉模式下，专注和精力恢复效率下降"

    # 覆盖层可以叠加（多个 overlay 同时触发时，乘积生效）
    - id: "高压模式"
      priority: 120
      when:
        all:
          - key: "subjective.压力"
            op: gt
            value: 60
          - key: "subjective.专注"
            op: lt
            value: 45
      apply:
        - match_intent: "focus_gain"
          op: multiply
          value: 1.4        # 高压低专注时，恢复性行为效果放大
        - match_intent: "stress_relief"
          op: multiply
          value: 1.2

  # 边界约束
  bounds:
    "subjective.情绪": [0, 100]
    "subjective.专注": [0, 100]
    # ... 每个维度都需要声明边界

  # 初始状态模板（多个，对应不同的起始场景）
  initial_state_templates:
    - id: "init_default"
      name: "默认初始"
      state:
        "subjective.情绪": 60
        "subjective.专注": 60
        "subjective.动力": 55
        # ...

    - id: "init_low_energy"
      name: "低能量初始"
      state:
        "subjective.精力": 35
        "subjective.情绪": 40
        # ...

  # 目标状态模板
  target_state_templates:
    - id: "target_focus"
      name: "提升专注"
      state:
        "subjective.专注": [70, 100]     # 目标区间，不是单点
        "subjective.动力": [50, 100]
        # 未声明的维度不参与目标判定

    - id: "target_relax"
      name: "放松恢复"
      state:
        "subjective.情绪": [70, 100]
        "hormone.皮质醇": [0, 40]
```

### 2.2 设计原则

- **维度名用点分路径**（如 `subjective.情绪`），天然支持分组建模，不限制分组数量；
- **目标状态是区间而非单点**，给了路径规划一定的容错空间；
- **overlay 规则基于意图类型而非具体事件**，使规则与事件脱耦——新增事件自动继承所有匹配的覆盖规则；
- **初始状态模板化和目标状态模板化**，支持一键切换运行场景。

## 三、第二层：事件库层（Action Library Layer）

事件库是被框架调用时执行的基本单元。每个事件声明它的触发条件、自身属性、以及对状态的影响。

### 3.1 事件定义

```yaml
# event_library.yaml
events:
  - id: "evt_my_action"
    name: "动作名称（人类可读）"
    type: leaf              # leaf | sequence | egroup

    # ── 执行属性 ──
    duration:               # 执行耗时（不同领域单位不同）
      value: 4
      unit: seconds         # 心智领域用秒；健身领域可能用分钟；午餐领域用分钟

    cooldown:               # 冷却：执行后多长时间内不可再次调用
      value: 0
      unit: events          # 按事件计数冷却，或按时间冷却

    # ── 状态影响（delta）──
    delta:
      "subjective.专注": 8
      "subjective.动力": 3
      "subjective.压力": -2
      "hormone.多巴胺": 2
    # 注意：这里的 delta 是「基础值」，实际生效时会经由 effect_mapping
    # 和 overlays 的乘数修正。这是框架的核心计算链：

    # ── 意图声明（用于被 overlay 规则匹配）──
    effects:
      - intent: "focus_gain"
        value: 8
      - intent: "motivation_gain"
        value: 3
      - intent: "stress_relief"
        value: 2
      - intent: "dopamine_gain"
        value: 2

    # ── 元信息 ──
    tags:
      - "心智模拟"
      - "恢复"
    content: "用短时专注冲刺把状态拉回主线，并积累一点动机。"

    # ── 可选：前置条件 ──
    preconditions:            # 仅当满足条件时才纳入事件筛层的候选
      all:
        - key: "subjective.精力"
          op: gt
          value: 20          # 精力太低时不能执行高消耗行为

  # ── 序列型事件（把多个叶子事件打包成一条链）──
  - id: "seq_stress_recovery"
    name: "压力恢复链"
    type: sequence
    steps:
      - "evt_request_help"         # 引用其他事件 id
      - "evt_background_incubate"
      - "evt_immersive_recover"
      - "evt_assembly_line"
      - "evt_eat_frog"
```

### 3.2 事件库的领域适配

同一个框架结构，注入不同的事件定义即可切换领域：

| 领域 | 事件示例 | duration 单位 | delta 含义 |
|------|---------|---------------|-----------|
| **心智** | 呼吸重置、步行补能、专注冲刺 | seconds | 情绪/专注变化量 |
| **午餐** | 鸡胸肉沙拉碗、番茄牛腩汤 | minutes | 饥饿度/饱腹感/清醒度变化量 |
| **健身** | 深蹲5组、跑步30分钟、拉伸 | minutes | 疲劳度/体脂率/训练意愿变化量 |
| **理财** | 预算审计、记账、定额储蓄 | minutes | 财务焦虑/储蓄率/消费克制变化量 |

每套事件库是一个 YAML 文件，框架加载后无需改动任何代码。

## 四、第三层：路径规划层（Path Planner Layer）

这是框架中最核心的算法层。输入当前状态和目标状态，输出若干条候选行为链。

### 4.1 规划器的核心算法逻辑

```
输入：
  S_current  = 当前状态向量
  S_target   = 目标状态（区间）
  E          = 事件库（所有可选事件）
  B          = 边界约束
  O          = 覆盖层规则集
  max_steps  = 最大步数
  k          = 输出候选数量

算法流程：

1. 【事件筛层】
   对于每个 e ∈ E：
     - 检查 e.preconditions 是否满足 S_current
     - 检查 e.cooldown 是否到期
     - 通过的事件进入候选集 E_candidate

2. 【路径搜索】  (A* 或 BFS 或 遗传算法，可配置)
   从 S_current 出发，搜索不超过 max_steps 的事件序列，
   每步的状态转移为：
     S_next = S_now + e.delta × O(S_now)
   其中 O(S_now) 是当前状态触发的所有 overlay 乘积。

3. 【目标判定】
   若 S_next 的所有目标维度的值都在 S_target 声明的区间内，
   则该序列为「达标路径」。

4. 【评分与排序】
   对每个达标路径计算评分：
     score = α × (1 / 步数)                 # 步数越少越好
           + β × (1 / 总时长)                # 耗时越短越好
           + γ × (超出的状态余量)             # 目标维度超出最低值的部分
           - δ × (副作用惩罚)                # 非目标维度的负向变化
   按 score 降序，取前 k 条作为输出。

5. 【输出】
   返回 k 条候选路径，每条包含：
     - path: [event_id1, event_id2, ...]
     - projected_final_state: S_final
     - score: 分数
     - side_effects: 非目标维度的变化摘要
```

### 4.2 路径规划的配置层

```yaml
# planner_config.yaml — 注入不同的搜索算法和评分权重
planner:
  algorithm: "astar"           # astar | bfs | genetic | monte_carlo
  max_steps: 40
  candidates_count: 3          # k — 输出几条候选供随机层选择

  # 评分公式的权重（注入不同领域偏好）
  scoring:
    step_count_weight: 0.4     # α — 少步数的重要性
    duration_weight: 0.2       # β — 短耗时的重要性
    surplus_weight: 0.25       # γ — 超目标余量的重要性
    side_effect_penalty: 0.15  # δ — 副作用的惩罚权重

  # 副作用惩罚的维度白名单（只有白名单内的维度变化会被计入惩罚）
  side_effect_dimensions:
    - "subjective.压力"
    - "hormone.皮质醇"
```

### 4.3 不同领域的评分偏好

同一个框架，通过修改评分权重适配不同领域的价值取向：

| 领域 | α (步数越少越好) | β (耗时越短越好) | γ (超目标余量) | δ (副作用惩罚) | 含义 |
|------|------------------|------------------|----------------|----------------|------|
| **心智修复** | 0.4 | 0.1 | 0.25 | 0.25 | 效果优先，不赶时间，副作用要严控 |
| **午餐** | 0.1 | 0.6 | 0.2 | 0.1 | 快速出餐最重要，吃的热量在范围内即可 |
| **健身增肌** | 0.2 | 0.3 | 0.4 | 0.1 | 动作质量/容量比次数重要，超目标意味着更多增肌刺激 |
| **应急场景** | 0.6 | 0.3 | 0.05 | 0.05 | 两步内稳定、其他都不重要 |

## 五、第四层：随机层（Randomization Layer）

随机层是整个框架的连接枢纽。它接收路径规划层产生的 k 条候选链，从中选择一条交付给执行层。

**它的职责不是创造选项，而是从已经算好的选项中抽签。** 这就是「系统算好几套基础，骰子随机一个方向发展」的确切含义。

### 5.1 随机策略的可配置性

```yaml
# random_config.yaml
random:
  strategy: "uniform"          # 可注入不同策略

  # ── 策略列表 ──
  # uniform         : k条候选等概率
  # weighted        : 按路径规划层的 score 分配概率权重
  # epsilon_greedy  : (1-ε) 概率选最高分路径，ε 概率等概率选
  # deterministic   : 永远选最高分路径（本质上关闭随机层）
  # coin            : 二选一抛硬币（k 必须为 2）

  strategy: "weighted"
  epsilon: 0.15                # 仅 epsilon_greedy 使用

  # ── 随机源 ──
  source: "crypto"             # crypto | time | user_input
  # crypto  : 使用系统随机数（适用于软件模拟）
  # time     : 用当前毫秒数取模（轻量）
  # user_input: 要求用户执行物理掷骰子动作（适用于需要认知隔断的场景）

  # ── 认知隔断配置 ──
  cognitive_separation:
    enabled: true              # 是否启用认知隔断（骰子掷出后不可改）
    display_mode: "blackbox"  # blackbox | transparent
    # blackbox    : 执行者只看到结果，看不到整个候选集
    # transparent: 执行者可以看到所有候选和概率，但仍须接受随机结果
```

### 5.2 随机层的两阶段模型

```
阶段一（设计者时段）:
  路径规划器产出 k 条候选链
  → 设计者可以审阅并批准/拒绝候选集（但不能在 k 条之外的扩充）
  → 设计者设置随机策略和参数

阶段二（执行者时段）:
  骰子激活 → 从 k 条中抽选一条
  → 选定后立即密封
  → 执行者沿选定的链逐事件执行
  → 密封期内不可更改

大前提：随机层永远不能自己发明新事件或新路径。
        它只能从路径规划层已经算好的候选集中选择。
```

### 5.3 为什么随机层的输入必须是「已算好的候选」

如果骰子可以自由选择任意事件组合，那它不是随机层，而是**赌博**——执行者可能在毫无边界的状态下随机组合出低效甚至有害的行为链。

如果骰子只能在规划器产出的一组候选（例如 k=3）中选择，那它就是一个**受控的扰动**——无论掷出哪一面，得到的都是一条经过算法验证的、可抵达目标的、副作用在可接受范围内的路径。

这就是随机不是任意，黑盒不是盲盒。

## 六、第五层：执行层（Execution Layer）

执行层完成「接受一条行为链 → 逐事件执行 → 实时记录状态变更 → 检查点介入」的完整流程。

### 6.1 执行器接口

```yaml
# executor_config.yaml  — 执行参数
executor:
  mode: "sealed"               # sealed | open
  # sealed: 密封模式，执行期间不可修改事件或路径
  # open  : 调试模式，允许手动跳过/替换事件

  tick_unit: "event"           # event: 按事件推进；time: 按时间推进
  auto_advance: false          # true: 自动推进到下一步；false: 等待用户确认

  checkpoint:
    interval: 5                # 每执行多少个事件触发一次检查点
    auto_evaluate: false       # true: 检查点自动比较预期与实际

  recording:
    log_state_delta: true      # 是否记录每次执行后的状态变化
    log_timestamp: true        # 是否记录时间戳
    log_notes: true            # 是否允许执行者附加手动备注
```

### 6.2 执行流程伪代码

```python
def execute_run(run):
    for i, event_id in enumerate(run.path):
        event = event_library[event_id]

        # 1. 计算本事件的预期效果
        base_delta = event.delta
        overlay_multipliers = evaluate_overlays(run.current_state, event.effects)
        actual_delta = {k: base_delta[k] * overlay_multipliers.get(k, 1.0)
                        for k in base_delta}

        # 2. 展示事件指令给执行者
        show_to_user(event.description)

        # 3. 等待执行完成
        wait_for_completion(event.duration)

        # 4. 记录
        record = {
            "event_id": event_id,
            "expected_delta": actual_delta,
            "reported_delta": collect_user_feedback(),  # 可选
            "timestamp": now(),
        }
        run.records.append(record)

        # 5. 更新状态
        run.current_state = clamp(
            {k: run.current_state[k] + actual_delta[k] for k in actual_delta},
            bounds
        )

        # 6. 检查点
        if i > 0 and i % run.checkpoint_interval == 0:
            decision = run_checkpoint(run)
            if decision == "abort":
                break
            elif decision == "adjust":
                # 密封到下一个检查点
                reseal(run)
```

### 6.3 执行层不负责什么

- 不负责质疑事件的有效性（那是设计者的事）
- 不负责评估「有没有更好的路」（那是路径规划层的事）
- 不负责比较「另一条链会不会更好」（随机层已经选定了）

执行层的唯一职责是：**让封装好的链跑完。**

## 七、第六层：反馈闭环（Feedback Loop Layer）

反馈闭环是整个框架的「自我校准引擎」。没有它，系统用久了会漂移——事件的 delta 基于初始假设，实际效果可能与假设不符。

### 7.1 反馈数据的产出

每次执行事件后，系统获得两条数据：

```
预期的 delta: 算法根据 base_delta × overlay 计算得到
实际的 delta: 执行者事后报告（或客观测量）的状态变化
```

### 7.2 校准逻辑

```python
def calibrate(event_id, expected_delta, actual_delta, n_samples):
    """
    当同一个事件的 N 次执行记录中，
    actual_delta 与 expected_delta 持续偏差超过阈值时，
    调整该事件的 base_delta。
    """
    error = actual_delta[k] - expected_delta[k]
    if abs(error) > threshold and n_samples >= min_samples:
        # EMA 平滑更新
        event.delta[k] = event.delta[k] + learning_rate * error
```

这适用于已被证实系统性偏差（如「步行补能」被高估，或「专注冲刺」被低估）。

### 7.3 overlay 规则的自进化

如果有足够多的执行记录表明：某个 overlay 规则（如「缺觉模式下的专注打折率 0.75」）在不同人群中偏差很大，这个规则可以从「硬编码」转化为「可学习的参数」：

```yaml
overlays:
  - id: "sleep_deprived_focus_penalty"
    when: ...
    apply:
      - match_intent: "focus_gain"
        op: multiply
        value: 0.75
        learnable: true          # 标记为可学习
        learned_range: [0.5, 0.9] # 学习范围
        learning_rate: 0.02
```

这就像引入参数学习迭代，把 overlay 从一个「设计者直觉」变成一个「数据验证过的修正因子」。

## 八、配置层：一根配置文件，启动一个领域

当七层都有了可插入的接口之后，整个框架只需要一根配置文件就能启动。

### 8.1 示例：午餐领域的配置文件

```yaml

  - "./lunch/recipes_protein.yaml"
  - "./lunch/recipes_balanced.yaml"
  - "./lunch/recipes_carbs.yaml"
  - "./lunch/recipes_light.yaml"
  - "./lunch/recipes_warm.yaml"
  - "./lunch/recipes_clean.yaml"

planner:
  config: "./lunch/planner_config.yaml"
  candidates_count: 3                # 输出3条候选菜谱

# ── 第四层：随机层 ──

  config: "./lunch/random_config.yaml"
```

## 九、与设计者/执行者分离的对位关系

回顾整个系列的主题——设计者与执行者的分离——现在可以画出最完整的对位表：

| 框架层级 | 归属 | 设计者的工作 | 执行者的工作 |
|----------|------|-------------|-------------|
| **状态指标层** | 设计者 | 定义维度、边界、overlay 规则 | 照实填写当前状态值 |
| **事件库层** | 设计者 | 创建/校准/淘汰事件模板 | 按指令执行单个事件 |
| **路径规划层** | 设计者 | 选择搜索算法、设定评分权重、生成候选链 | 不知道完整候选集 |
| **随机层** | 中间地带 | 设定随机策略和参数 | 掷骰子，接受结果 |
| **执行层** | 执行者 | 设定密封参数和检查点间隔 | 逐事件执行、不可修改 |
| **反馈闭环** | 设计者 | 在校准时段查看趋势、调整参数 | 照实记录、不分析 |
| **配置层** | 设计者 | 组合以上各层为配置文件 | 不知道配置文件存在 |

**随机层是唯一由双方共同参与的层——设计者决定怎么掷，执行者负责掷。** 这正好是密封指令在术层的最精确实现：设计者设定密封的规则和边界，执行者在规则内拥有不可上诉的随机选择权。

## 十、框架以三层解耦思路实现

```text
        ┌──────────────────────┐
        │   配置层 (YAML)       │  ← 领域专属数据，零代码变更
        │  · state_schema       │
        │  · event_library      │
        │  · planner_config     │
        │  · random_config      │
        │  · executor_config    │
        └──────────┬───────────┘
                   │ 注入
        ┌──────────▼───────────┐
        │   引擎层 (Python/TS)  │  ← 框架通用代码，不随领域变化
        │  · StateEvaluator     │
        │  · PathPlanner        │
        │  · RandomSelector     │
        │  · SealedExecutor     │
        │  · FeedbackCalibrator │
        └──────────┬───────────┘
                   │ 驱动
        ┌──────────▼───────────┐
        │   界面层 (UI)         │  ← 设计者界面 / 执行者界面双模式
        │  · 状态快照面板        │
        │  · 事件执行卡片        │
        │  · 骰子交互组件        │
        │  · 趋势仪表盘          │
        └──────────────────────┘
```

配置层是纯数据，引擎层是纯逻辑，界面层是纯交互。三者通过明确定义的接口通信。

当你想把框架从午餐切换到健身，唯一需要做的事是：写一套新的 `config_fitness.yaml` 和它的配套 YAML 文件。引擎层和界面层的代码**一行都不用改**。

## 十二、总结

这两个系统（午餐、MindFlow）走到现在，已经证明了同一套范式可以在两个完全不同领域运转。它们不是两个独立的设计，而是同一个通用框架的两次不同实例化。

这个框架的核心是一个简单的循环：

```
当前状态 → 事件筛层过滤可选事件 → 路径规划生成 k 条候选链
  → 骰子从 k 条中选一条 → 密封执行 → 记录效果 → 反馈校准 → 新的当前状态
```

而它的价值在于：**这个循环中的每一步，都是可替换的插件。**

换一套状态指标，它就变成了午餐系统。换另一套，它就变成了健身教练。再换一套，它就变成了理财规划师。引擎层不需要知道自己在做什么领域——它只知道自己在操作一个有坐标的状态空间、一个有 delta 的事件库、一个可搜索的路径图、一个可掷骰子的随机层。

这正是「设计者不设计答案，设计者设计系统」在工程层面的最终展开：设计者写的不是「今天吃什么」，也不是「今天做什么行为」，而是**让这些答案被自动生产出来的制度框架**。骰子负责在这套制度中选择一个具体方向，执行者负责把选定的方向跑完。

什么都不用再想了。掷骰子，然后吃。掷骰子，然后做。
